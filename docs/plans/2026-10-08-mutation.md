# Mutation Records And Test Runner Implementation Plan

**Goal:** Record all system planting/harvesting per account and provide a cancellable, non-resumable mutation experiment.

**Architecture:** Common farm operations write an account-local durable journal with system-assigned increasing IDs. An account Worker owns the test runner and farm operation gate. Admin APIs read records offline and dispatch test commands to the existing Worker; Vue views poll only while visible.

**Tech Stack:** Existing Node/CommonJS, filesystem persistence, Worker RPC, Vue/Pinia, Node test runner.

## Requirements

- Plant success inserts; harvest snapshots mutations before sending, finalizes only confirmed harvests. Unmatched historical harvests are ignored.
- Records include account, sequence, seed, land, timestamps, source, test/round, status, mutation IDs/names/count. Unknown is not zero.
- All system planting and harvesting use the recorder. No special test-only records path.
- Test supports only known single-cell/single-season bag seeds, target 1-3000, default delay 200ms between lands.
- Online account, empty unlocked lands, sufficient seeds, farm/fertilizer/land upgrade disabled.
- Farm mutation gate prevents conflicting manual/background operations and configuration changes.
- Plant all eligible lands up to remaining target; normal fertilizer pass, organic passes until confirmed maturity; farming, harvest, dead-plant cleanup. Finish the final harvest even when planting target reached.
- Stop/errors/disconnection/restart terminate without resumption. Settle in-flight responses but issue no subsequent mutations.
- Per-account records page, mutation/status filters, pagination, chronological CSV export, visible-page refresh.
- Account settings task controls show separate planted/harvested counts and errors.

## Steps

1. Add journal repository and tests for allocation, account isolation, matching, missing history, filtering, export ordering.
2. Add operation gate and injectable runner with tests for partial last round, fertilizer pass ordering, cancellation, resources, failures, no recovery.
3. Connect common farm operations, Worker lifecycle, guarded config updates, access-checked routes.
4. Add Vue record page and account settings controls using existing UI conventions and local seed/mutation assets.
5. Run focused and full offline tests, frontend typecheck/build, non-mutating lint/diff checks. Do not use real accounts or browser acceptance; user verifies layout and gameplay.

## Persistence And Acceptance

- Records follow the repository's file-backed persistence pattern, not a new SQL dependency. Each account has `mutations/<hex-account-id>/records.jsonl` under the data directory. The account Worker is the sole writer; IDs are allocated monotonically by storage, survive restarts, and are not reset between tests.
- `test.json` retains configuration and terminal progress, but never resumes an interrupted run. Unknown harvest outcomes are distinct from confirmed zero-mutation harvests.
- Final mutation snapshots are reserved before Harvest and finalized after confirmation. Unmatched historical harvests do not create records.
- The protocol has no immutable crop-instance identifier. Matching uses the current local planting record, plant/season and observed phase progression. An entirely unobserved same-seed replacement in the official client cannot be conclusively distinguished.
- Restart the backend manually to load the new handlers; the existing backend/real accounts were not restarted.
- Manual acceptance remains: desktop/mobile layout, real seed availability, successful ordinary planting/harvest records, test start/stop, final partial round, visible-page refresh and CSV contents. Multi-cell and multi-season seeds are excluded from test selection and rejected by the backend.
